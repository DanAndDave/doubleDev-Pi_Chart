# Every Briefing stays where it was sent

Supersedes ADR-0010's "the next Call replaces that block".

On Claude Opus 5.5 a thinking block stays valid only while everything sent before it is unchanged on later requests. Under ADR-0010 the Briefing sat before the thinking each Call produced, and the next Call replaced it. So the API dropped every thinking block in a pi-chart Conversation (53 drops over 11 Calls, none in plain omp; `openspec/changes/archive/2026-10-13-pack-parts-follow-the-turn/evidence/thinking-binding.md`). The model lost its own earlier reasoning on every Call and spent output tokens to re-derive it.

**Every Call's Briefing is now sent again on every later Call that still sends the message it follows: in its original position, byte for byte, and cleared.** A cleared Briefing is a turn-scoped system message (`clear_at: "next_user_message"`). Anthropic documents that a cleared message "adds nothing to what the model sees and costs no input tokens", but because it stays in the array, the thinking after it stays valid. The model still reads only the current Call's Briefing. In a proxied three-Turn run, Briefings kept identical dropped no thinking blocks. A control whose Briefing changed on every Call dropped one, then two (`openspec/changes/archive/2026-10-13-keep-thinking-blocks-valid/evidence/turn-scoped-feasibility.md`).

## Considered options

- **Replace the Briefing every Call (ADR-0010).** Every thinking block is dropped.
- **Keep only the current Turn's Briefings.** Thinking is still dropped at every Turn boundary, which is where recall changes and the most reasoning is lost.
- **Store sent Briefings in the Thread Store.** Easier to query, but the Thread Store is an index that can be dropped and rebuilt (ADR-0002), and Briefings would stop working without Postgres.

## Consequences

- A sent Briefing can't be rebuilt, because the Stores it was assembled from have changed since and each `-c` Turn is a new process. Each one is stored exactly as it was sent and re-sent from that copy. This is a new kind of record. Like a Pin (ADR-0009), it lives in the Journal as a custom entry, `pi-chart.briefing`; a text already stored is referenced by hash rather than written again.
- A stored Briefing names the Journal entry id of the message it follows, not a Call address, so on `/tree` it is sent only when that message is on the active branch. Every entry is written inside the `context` hook, before the request goes out, so no sent Briefing exists only in memory and none is lost if the process dies. On a Turn's first Call the prompt isn't in the Journal yet: omp flushes it after the hook returns, so the entry lands before it. That entry marks that it precedes the prompt, with the prompt's timestamp, and resolves to the first message written under it. A first Call's entry is therefore an ancestor of its prompt and lies on every path that copies the prompt. Should omp ever flush the prompt first, the entry's parent is the prompt, recognised by its timestamp, and it resolves to that instead.
- A Briefing that should be sent but has no stored copy is not replaced: nothing is sent in its place, and the thinking after it drops. A substitute would differ byte for byte, so it would save no thinking. Accounting counts it as missing, beside the count and size of earlier Briefings sent again.
- A branch, a fork at an entry and `/btw` promotion copy only the path to the leaf, keeping entry ids. A Briefing's entry is written after the message it follows, so it can lie off the copied path while its message lies on it. Like Pins, Briefings are therefore read from the whole Journal, not the branch, and carried into a new Journal explicitly: those whose message is on the copied path, with the texts they reference.
- Budget and Ceiling cover only the current Briefing. A cleared Briefing adds nothing to `usage.input_tokens` or to a token count, so earlier Briefings are outside the Budget, the Ceiling and the Floor.
- A Briefing leaves with the message it follows: when tail eviction drops that message, the Briefing is no longer sent. Eviction already drops the thinking after it, so nothing more is lost, and a request carries at most one cleared Briefing per Call in the verbatim tail. Those aren't billed and the model doesn't read them, but they are bytes on every request; keeping them for the whole Conversation would eventually exceed the Messages API's 32 MB request limit.
- Whether a Call works this way is decided from that Call's model: only models whose compat flags declare both mid-Conversation and turn-scoped system messages. On any other model the Call falls back to ADR-0010: one Briefing sent as a user message, replaced on the next Call, and no stored Briefings sent. Stored Briefings stay in the Journal untouched, and are sent again when a later Call's model has the flags; the other model's thinking is already invalid there, so nothing is lost.
- The Briefing has to be a single message: omp sends a turn-scoped message only when an assistant message or the end of the array follows it. Everything in it therefore carries system authority, not user authority: the Pins, but also retrieved text the user never wrote — tool output inside recalled Turns, Doc Store text, the codebase structure. Anthropic warns that a system message is not a place for untrusted content. The Briefing fences it: a fixed preamble states that everything after a marker is reference data, not instructions, and only the framing and the Pins sit before the marker. The fence is part of the Briefing's text, so it never changes once sent. It reduces prompt injection through retrieved content but doesn't remove it; that risk is accepted.
- This removes only the drops the Briefing causes. Thinking is still dropped whenever an earlier message changes: tail eviction, Elision of the Turn in progress, a tail copy that doesn't serialise byte for byte, or a Call that fails open.
